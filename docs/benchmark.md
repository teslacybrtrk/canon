# Benchmark (simulated): Canon against merge queues, and Canon with each mechanism switched off

Generated by `scripts/benchmark.mjs` on 2026-10-13 at revision `aed2d4e076d4`, with data: 2 orders × 1 repeat, one process at a time (the data workload re-run alone after a harness fix); stateless: 3 orders × 1 repeat, 7 processes in parallel on one Mac (outcome counts; elapsed time under contention); integration: 2 orders × 1 repeat, 7 processes in parallel on one Mac (outcome counts; elapsed time under contention); coordination: 3 orders × 1 repeat, 7 processes in parallel on one Mac (outcome counts; elapsed time under contention) (order 1 as written, the others seeded shuffles, the same for every system; a repeat runs the same order again, and differs only through timing and the repair model). Raw results: [docs/benchmark/](benchmark/). The harness the runs used is committed in `6e15b3a`; the `revision` field in each raw file is the checkout's HEAD when that run started, before the last harness edits were committed. Objectives, tolerances and metric definitions, written before this run: [docs/benchmark-objectives.md](benchmark-objectives.md). **This is a simulation of the pipelines on local Workers**, not deployed Canon: the release candidate is a copy of production's local storage, the rehearsal replays the facts, and the canary compares raw error rates instead of routing a share of traffic. The deployed, end-to-end run is [docs/e2e.md](e2e.md).

Every system gets the same attempts, the same protected checks (every canon fact plus the attempt's own, and the repo's CI), the same conflict repair (3-way re-apply, then the judge's repair model as a service), the same compute (one machine, sequential), and the same agent behaviour (an attempt whose own fact fails is resubmitted once, at the back). Production is a local Worker whose storage persists across releases, with user traffic between them.

**Systems.** *Strong merge queue*: tests each change on the merged tree with every protected check, then ships. *Merge queue with the same release safeguards*: the same, plus everything Canon does at release (a release candidate on long-lived data, a rollback rehearsal, a canary, a gate on destructive data changes): these aren't Canon's alone. *Canon*: the safeguards plus its coordination (a claim on a fact that's already canon is superseded instead of integrated; a claim waits for the facts it declares it builds on).

**Safely landed**: a feature in production at the end, every fact holding, whose release can be rolled back safely. **Wrong accepts**: a release that broke a fact in production. **Unsafe to roll back**: shipped releases whose previous version, run on production's data afterwards, broke a fact. **Needless rejects**: features Canon landed safely (same order) that this system didn't. **People**: conflicts nobody could repair, decisions routed to an owner. **Rejections / resubmissions**: attempts sent back, and of those the ones whose own fact failed that the modelled agent sends once more (events, not agent effort: no agent's time is measured). **Repairs / failed**: calls to the repair model, and calls that returned nothing usable. **Redundant**: attempts that delivered nothing new (a duplicate of a feature already in), and the checks and releases spent on them. **Seconds**: elapsed, under the stated conditions; only sequential runs are comparable. Several runs: mean (min–max).

## Reading it, against the objectives written before the run

The objectives, tolerances and metric definitions were committed before these runs
([benchmark-objectives.md](benchmark-objectives.md), `c4c9a2b`). Each is checked here against the tables above and the
raw results in [benchmark/](benchmark/).

1. **Safety is a constraint: met, and it's parity.** Canon had 0 wrong accepts, 0 unrecoverable incidents and 0
   releases unsafe to roll back in every run of every workload. So did the merge queue with the same release
   safeguards: on safety the two are equal, and this benchmark shows no safety advantage for Canon over a queue that
   has its release safeguards. The plain queue's failures (on the data workload, in both orders: a schema change that
   broke the market page on existing data, and a release that lost a shopper's basket for good, plus a migration left
   unsafe to roll back; on the stateless workload, a change failing one request in eight, in every order) are the
   release safeguards' doing, and the ablations show which: each mechanism switched off lets its own failure through.
2. **Delivery is not traded for efficiency: met.** In every order of every workload Canon delivered at least as many
   features safely as the safeguarded queue (needless rejects 0).
3. **Coordination saves work where it applies: met, against this baseline.** The modelled queues have no duplicate
   supersession and no dependency-aware scheduling; an advanced queue could implement both, and this doesn't show it
   couldn't. On the coordination workload, against the safeguarded queue,
   with the same 4 features delivered in every order: 133 checks against 160–173 (20% fewer), 4 releases against 5,
   1.7 repair calls against 3, and no rejection, where the queue tested the dependent change before its prerequisite,
   rejected it and had it resubmitted. Canon's own verification of the duplicate (its command fact and probes, 5
   checks) is counted. The work Canon avoids is the duplicate's integration, re-verification and release, and the
   failed test of the dependent change.
4. **No material regression elsewhere: met.** Canon's checks are the same as the safeguarded queue's on the data
   (257.5) and stateless (62.3) workloads, and 0.62 times on integration (576 against 923.5). The integration gap comes
   from duplicates: its 16 attempts build 8 features twice, the queues integrate every second copy (a queue doesn't
   know two changes build the same thing) and Canon supersedes them; the safeguarded queue also needed a person 2.5
   times per run, for text conflicts the repair model couldn't resolve on those duplicates. A team that closes
   duplicate pull requests by hand would narrow this gap; that's people's time, which isn't measured.
5. **Time only from controlled runs:** **met, by a small margin, against the safeguarded queue; not met against the plain queue.** In the sequential run (one benchmark process, nothing else on the machine; the coordination workload, 3 orders × 2 repeats, 6 runs per system; raw results in [benchmark/coordination-timing.json](benchmark/coordination-timing.json)), Canon took 83–130 s (mean 102), the safeguarded queue 137–291 s (mean 188) and the plain queue 122–226 s (mean 160). Canon's slowest run is faster than the safeguarded queue's fastest, which is the bar set in advance, but only by 7 s: an observed advantage in six runs per system, not a guarantee. Against the plain queue the ranges overlap, so there is no reliable time difference (and the plain queue has none of the release safeguards). No repair call failed for Canon or the safeguarded queue; one failed for the plain queue in one run, which then landed 3 features instead of 4. These are local, small workloads: read the times as relative, not as deployed latency.

**Execution conditions.** The data workload was re-run alone (one process) after a harness fix: the first, parallel
run counted a request refused by a just-restarted local server as a lost basket. The stateless, integration and
coordination outcome runs shared the machine with six other benchmark processes, so their elapsed times are under
contention and are not compared. Repair failures are counted per run in the tables (repairs / failed). Orders are
different arrival sequences; repeats (timing run only) are the same order again, and differ only through timing and
the repair model.

**What this establishes, and what it doesn't.** It is a simulation of the pipelines on local Workers, on small
workloads written by Canon's author, with merge trains not modelled for either system. It shows safety parity with an
equally safeguarded queue, and less verification and release work for the same delivered features where duplicates and
prerequisites occur. It doesn't show that Canon is better on every workload, or measure people's time. The deployed
evidence for the same coordination behaviour is [e2e.md](e2e.md).

# Benchmark: Canon against a strong merge queue, and Canon with each mechanism switched off

Generated by `scripts/benchmark.mjs` on 2026-10-13. Every system gets the same attempts in the same order, the same protected checks (every canon fact plus the attempt's own, and the repo's CI), the same conflict repair (3-way re-apply, then the judge's repair model as a service) and the same compute (one machine, sequential, local Workers). Production is a local Worker whose storage persists across releases, with user traffic between them.

**Safely landed**: a feature in production at the end, with every fact holding, whose release can be rolled back safely. **Wrong accepts**: a release that broke a fact in production. **Unsafe to roll back**: shipped releases whose previous version, run on production's data afterwards, broke a fact. **Needless rejects**: features Canon landed safely that this system didn't. **People**: conflicts nobody could repair, decisions routed to an owner.

## Reading it

**Where Canon is ahead.** On the stateful workload, the strong queue, with every protected check Canon has and the
same repair, shipped two releases that broke production: a schema change that only fails on data that already exists
(the market page returned 500 for every shopper), and a "schema reset" that dropped the basket table, losing a
shopper's basket for good (a rollback restores code, not data). It also shipped a data migration that left production
unsafe to roll back. Canon shipped none of those: its release candidate (with long-lived data) caught the first, an
owner declined the destructive change when the data gate showed them the line, and the rollback rehearsal caught the
migration. On the stateless workload the queue shipped a change failing one request in eight to every user; Canon's
canary took it back out at 10%.

**What each mechanism is worth.** Switching one off lets exactly its own failure through, and only that one: without
the release candidate, the schema break reaches production; without the rehearsal, the unsafe migration ships; without
the data gate, the basket is lost; without the canary, the flaky release goes out; without conflict repair, 3 of 8
features don't land and 6 conflicts wait for a person.

**Where it isn't.** On the integration workload (16 attempts, most of them re-applied onto a canon that had moved),
the strong queue lands the same 8 features as Canon: with the same checks and the same repair, a careful queue gets
the same code into main. Canon runs about twice the checks there (every release also runs a release candidate and a
rollback rehearsal), and needed a person once on the stateful workload (the destructive change), where the queue needed
none, and lost the data. Seconds vary from run to run on one machine (in an earlier run of the same script, Canon took
514 s on integration against the queue's 459 s); read them as rough.

**Limits.** One order per workload, small workloads written by Canon's author (the kinds of failure it was built to
catch are in them on purpose; the integration workload, where it shows no landing advantage, is in it too), sequential
local execution rather than Canon's parallel verification, and no measure of people's time beyond counting when one
was needed. The harness and the patches are in the repo, so anyone can change the order, add a workload, or switch
other mechanisms off.

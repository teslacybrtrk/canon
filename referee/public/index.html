The problem

Code review was built for a few humans. Agents break it.

Pull requests assume a person reads every change. Put dozens of agents on one repo and that person becomes the bottleneck, or stops really reading.

With pull requests today

Review is the bottleneckEvery agent change waits for a person to approve it, and agents write more diffs than anyone can read.
A clean merge can still breakGit merges text, not behaviour. Two changes that each pass can merge without a conflict and break the product together.
Agents can grade their own workBy default the tests that judge a change ship inside it, so an agent can edit them, and agents have been measured doing it.
Intent is proseAn issue says what an agent means to do, but nothing checks it, or tells you two agents want contradictory things.

With Canon

Machines verify, people decide rulesEvery push is checked against every fact automatically. People review changes to the rules; the code comes along as evidence.
Conflicts are contradictionsThe referee judges the exact tree that becomes main, so a change that breaks a fact is caught even when it merged cleanly. Text conflicts stay the agent’s chore; only contradictions reach a person.
The checks are out of reachFacts are owned by canon, never by the branch. Changing one is a separate, explicit revision a person approves.
Intent comes firstAgents claim the fact they’re making true before writing code, so everyone sees who is doing what, and the referee says when it’s done.

How Canon works

Four moves. Any agent that speaks Git can play.

The repo is still Git and the agent still pushes. The only new object is the fact: a plain sentence plus a check that runs against a live preview of the app.

  1. Read the canon

    The facts that are true of production right now, and what other agents are already working on.

    ✓ The basket charges the listed price
    ✓ A sold-out item can’t be added

  2. Claim a fact

    An agent declares the one new fact it will make true. Canon gives it a private world: a fork with its own Git remote.

    agent-2 → “A stall cannot be double-booked”
    world farmstand-p2q8zz

  3. Push a world

    Plain git push. Every commit becomes its own live preview on Cloudflare.

    $ git push origin main
    → preview built in ~40 s

  4. Get a verdict

    Canon runs every fact on the preview. Keep them all and add yours: a person can accept it into production.

    READY · 6 kept · +1 new
    REJECTED · ✗ listed price

The service that runs every check and keeps the canon. It decides what is true; it never merges code.
Who makes the decisions?

Agents decide what to attempt. The referee decides what is true: it runs every fact against the world’s live preview and rejects any world that breaks one, automatically. A person decides what becomes canon by accepting a fact.

Agents propose, the referee checks, people decide what must stay true.

Who writes the facts?

The starting facts live in the repo as canon.json. After that, agents propose new facts as part of their claims, each with its check. A fact only becomes canon when a person accepts a world that makes it true.

A proposed fact whose check already passes on canon is refused: if it can’t fail, it isn’t a new fact.

What if the product’s behaviour needs to change?

Canon doesn’t stop behaviour from changing; it stops it changing by accident. An agent that wants a new rule proposes a revision: a fact that replaces an existing one (“the listed price” becomes “the listed price, with 10% off lines of 10 or more”). Its world may break the old fact; the verdict shows “retires X”, and a person approves the rule change. The old fact is kept in history with who replaced it and why.

Who reviews, and who verifies?

Verifying is automatic. On every push the referee builds a preview of that exact commit, runs every fact, checks the world’s canon.json, and confirms a proposed fact actually fails on canon. No AI judges anything: random inputs are drawn from the commit’s own hash, so the same commit always gets the same checks.

Reviewing is human, and it starts with rules, not diffs. A person sees the new fact in plain words, its short check, the fact diff and a live preview. Reviewing a five-line check is far easier than a 500-line diff. Facts settle behaviour, not taste: for anything a check can’t judge, the code is one click away.

What about lint, types, performance and database changes?

They’re facts too. This demo’s canon includes “the code passes the linter, with no rules silenced”, “the code type-checks”, “the toolchain, its settings and the deploy config only change by revision” and “the market page answers in under 400 ms at p95”. Database rules fit the same way: “migrations only add, never drop”, “every migration applies cleanly to a copy of the data”.

Facts can be scoped to files, so a rule about database code is only judged on worlds that change database code. Agents run canon read --for <file> to see which rules govern a file before touching it. Judgement about design quality can’t be reduced to checks; Canon keeps that as a review, not a pretence.

How do you write facts for a big, complex codebase?

You don’t write them all up front. Start with the few dozen invariants where a silent break is expensive (money, permissions, data integrity, critical flows). After that, every accepted change adds a fact, so the spec grows as a side effect of shipping, each fact linked to the change and reason that introduced it. Existing tests become command facts.

Facts only protect what they assert, just like tests. The difference is that every behaviour change that is captured is deliberate, reviewed and explained.

Isn’t Git plus enforced test coverage enough?

For a few humans, often yes. With agents, two things break. By default the tests that judge a change ship inside it, so an agent can edit them; platforms can lock test files, but then a person has to review every test edit. And coverage measures which lines ran, not whether anything meaningful was checked; an agent can reach 90% with tests that assert almost nothing.

In Canon the checks are owned by canon, out of the agent’s reach, and a fact that can’t fail is refused. Coverage still fits: “coverage stays above 80% on changed files” is just another command fact.

Can’t an agent just weaken a check to pass?

No. The referee judges every world with canon’s copy of the facts, never the world’s own. A world whose canon.json changes, drops or invents a fact is rejected as tampered. Command facts call tools directly, and a fact pins the toolchain, its settings and the deploy config, so a world can’t swap the linter. Suppression comments are ruled out by facts too.

Gaming a check is the harder problem, as with any test. Probes draw random inputs from each commit’s hash, so hard-coded answers fail; facts that only read are sent exactly as a visitor’s requests; and canon’s facts are re-checked on production every hour.

What happens when two agents edit the same file?

Each works in its own world, so nothing happens until one lands. Then the other is behind: canon refresh replays its changes on the new canon, and the agent resolves any text conflict itself, as in a rebase. A person only hears about contradictions: worlds whose facts can’t both hold. A refreshed world that breaks the accepted fact is rejected without anyone reading it.

What if canon changes while an agent is still working?

Its world is marked behind canon, not rejected: it simply predates the new fact. canon refresh makes a fresh world from the current canon and re-applies the agent’s changes; the agent resolves any conflict and pushes again.

Is this a new Git? Does it replace GitHub?

No. The code is an ordinary Git repo and agents use plain git push. Any Git client works, a person pushing by hand is just another world, and the repo can still be mirrored to GitHub as an archive. The only new object is the fact.

Does it only work for web apps?

No. A fact has one of two kinds of check: HTTP requests against the commit’s live preview, or a command run on the commit’s code in a clean container: lint, type-check, a test suite, a coverage threshold, a bundle-size limit. If it can fail, it can be a fact.

Can it run with no human in the loop?

Yes, with a policy in canon.json: "autoAccept": "backlog". People write a backlog of facts they want; agents race to make them true, and the first world that keeps every canon fact and makes one true lands on its own. Humans decide what must be true; agents decide how.

Facts that agents propose themselves still wait for a person, so an agent can’t lower the bar by inventing an easy rule.

How would this scale to thousands of agents?

Attempts scale out: each is a cheap Artifacts fork with its own preview, and checks run in parallel. Accepting is deliberately one at a time, so canon is always one consistent world, and each accept sends the worlds in flight to refresh. Merge queues tame that churn with batching and speculative runs; that’s the next step here. The demo runs 5 to 8 agents.

Isn’t this just CI and branch protection?

Mechanically, close: it’s the old rule merge queues enforce, that only a tested tree lands. What changes is what’s tested and who decides. Facts are declared before work starts, owned by the referee instead of each branch, checked on a live preview of every commit, and changed only by a revision a person accepts. People review changes in facts, not code diffs.

Think of it as SWE-bench’s grading rule turned into a merge policy: a claim must go from failing to passing, canon must keep passing, and the referee owns both.

How is it kept safe?

An agent’s token can write only to its own fork. When a world is accepted, its write tokens are revoked, so canon can’t change underneath you. Every world, including rejected ones, stays readable and clonable as a record.

Anyone can read the referee; writing to it takes a key. An agent’s key can claim a fact but never accept one.

What does it run on?

Cloudflare Artifacts for every repo and fork, Workers and a Durable Object for the referee, Workflows and Containers for CI, Workers Previews for every commit, and R2 for build caches. The referee uses no AI model: a verdict is the result of the checks, not an opinion.
